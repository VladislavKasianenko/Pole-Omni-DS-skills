# Как устроен код проверки (src/audit.js)

Справка для тех, кто правит код проверки. Исходник — `src/audit.js`, в навык он попадает в сжатом виде внутри `ds-review/scripts/review.js` (сборка — `tools/build.mjs`). Настройки (блок `CFG` вверху исходника) прокомментированы прямо в коде.

`review.js` = проверка (`src/audit.js`) + пометки (`src/annotate.js`) в одном вызове `use_figma`: модели не нужно передавать находки из одного вызова в другой.

Скрипт только читает файл. Идёт по экранам по очереди и собирает находки `{ id, scr, r, s, m, fx, g }`, в конце сводит их в группы, то есть в будущие пометки.

## Разделы скрипта

| Раздел | Что делает |
|---|---|
| экраны | Корень — экран, секция или страница. В секции и на странице экраном считается фрейм шириной 300–480 px, вложенные секции тоже обходятся. Больше `maxScreens` экранов не проверяется |
| кэши | `vInfo` — тип токена (`ds`, `web`, `deprecated`, `primitive`, `unknown`), `sName` — имя стиля, `master` — мастер инстанса `{ mc, set, name }`, где `name` — имя набора вариантов или компонента |
| находки | `add()` складывает находку. Внутри компонента продуктовой команды находки копятся в `CAPTURE` и потом сводятся в одну. `checkPaints(n, prop, opts)`: `atId` — куда ставить пометку, `label` — подпись, `rule` — правило для hex |
| скругления | Секции должны быть на `container/section`. Блоки и карточки определяются по значению скругления: 20 → `container/block`, 12 → `container/card` |
| отступы | Контейнер с секциями — вертикальный автолейаут почти во всю ширину экрана, где минимум 2 секции разделены отступом или скруглены. Иначе это список строк, а не секции. При `SPACE_BETWEEN` gap не проверяется |
| кнопки и иллюстрации | `primaries` — Primary-кнопки текущего экрана. Кнопки внутри компонентов команд не считаются Primary экрана. Кнопки и иллюстрации ищутся и внутри 🍏 компонентов (Empty State, Bottomsheet). Порядок кнопок в вертикальном стеке — по важности сверху вниз |
| компоненты | Разбор инстанса по эмодзи и библиотеке, кастомизация, детач |
| компоненты продуктовых команд | Проверка состава компонента команды |
| обход | `walk()` возвращает уровень «картинности»: 0 — интерфейс, 1 — фигура, 2 — изображение, 3 — вектор |
| группировка | Сведение находок в пометки |

## Кастомизация

`checkOverrides` берёт из `overrides` инстанса поля, перечисленные в `CFG.badOverride`. Переопределение не считается кастомизацией, если:
- значение совпадает с мастером. Так бывает, когда тень выключили и включили или цвет поменяли и вернули. Слой мастера ищется функцией `twin()`: сначала по id (`I<инстанс>;<слой мастера>`), а для мастера из библиотеки, у которого id слоёв другие, — по тому же пути из индексов детей;
- это цвет иконки внутри 🍏 компонента, и он на 🍏 токене (`iconOnDsToken`). После замены иконки через свойство компонента Figma помечает её цвет как переопределённый, хотя цвет задаёт сам компонент. Сравнить с мастером здесь нельзя: содержимое вложенных иконок у мастера из библиотеки недоступно.

## Эмодзи компонентов

- 🍏 — актуальный компонент ДС. Локальная копия — `local-ds`.
- 🔥, 🔴, 🟥 или `[old]` в названии — устаревший компонент из Pole Mobile 1.0 (`deprecated-component`).
- 🏀, ⚽ — веб. 🔶 — служебная часть. 🍋 — Платформа, не проверяется.
- Любой другой эмодзи (🍔, 🖼️ …) или без эмодзи — компонент продуктовой команды. Иконки и иллюстрации распознаются по названию.

Раздетаченным компонентом (`detached`) считается фрейм с 🍏 или устаревшим эмодзи в названии. Фрейм с эмодзи команды обходится как обычный.

## Компоненты продуктовых команд

Свои компоненты команд разрешены, но собраны должны быть из 🍏: лейблы, чипы, строки списка, кнопки, токены, стили. Содержимое проверяется один раз на мастер-компонент, `prodCache` хранит результат по `mc.id`. Все нарушения внутри сводятся в одну находку `product-component` на каждую копию.

`lookalike()` ищет самодельные элементы и возвращает `[что это, чем заменить, гайд]`:
- лейбл или чип: фрейм с заливкой или обводкой и скруглением, высотой до 32 px, с одним текстом;
- кнопка: такой же фрейм высотой 36–56 px и шириной от 100 px с одним текстом;
- строка списка: горизонтальный фрейм от 200 px с текстами в столбик (заголовок и подпись) и иконкой или контролом в конце. Считается только если в столбике минимум 2 такие строки. Одиночная строка в карточке без шеврона, например промокод или описание, — не список, текст можно оставить.

`chevronRow()` работает и на экранах, не только внутри компонентов команд: горизонтальный фрейм от 200 px с текстом, у которого последний элемент (с заходом во вложенные горизонтальные фреймы) — иконка-шеврон (`CFG.chevron`). Это пункт 🍏 List или заголовок 🍏 Title со стрелкой.

Вложенный компонент команды показывается цепочкой: `«Label ads» → «Реклама» — текст без стиля`. Для этого находка хранит `p` (части) и `name`.

## Картинки и иконки

- Маленький вектор (до `iconMax`, 48 px) — иконка, hex на ней запрещён. Крупный вектор — часть картинки, hex допустим.
- Фрейм, внутри которого только векторы и изображения, — сложная картинка, hex внутри допустим. Если он не больше 48 px и состоит только из векторов, это самодельная иконка.
- Контейнер до 64 px с hex на векторах — иконка, собранная вручную: одна пометка вместо пометки на каждый вектор.
- Тень у самого экрана — оформление холста, не проверяется.

## Группировка

- Один и тот же элемент с одной проблемой — одна пометка на первом месте. Элемент — это мастер-компонент для инстансов, а для остальных слоёв — имя и ширина слоя (копии на разных экранах). Остальные места попадают в `more: [{ scr, name, id, n }]` по экранам.
- Разные элементы с одной проблемой на одном экране — не больше `maxIdsPerGroup` пометок, остальное считается в `similar`.
- `totals.groups` — сколько будет пометок. `errors`, `patterns`, `checks` — сколько мест всего.
- `skipped`: `platform` — компоненты 🍋 Платформы, `system` — системные элементы, `product` — копии компонентов команд, собранных из 🍏.
